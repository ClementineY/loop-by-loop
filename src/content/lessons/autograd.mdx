## PyTorch remembers how the answer was made

Now that a gradient has a concrete meaning, the next question is how PyTorch obtains it. The forward pass leaves a trail of the operations that produced the loss.

Use the four steps below in order. Watch which objects appear, where gradients are stored, and what gets cleared for the next batch.

## Read the trail in real PyTorch

```python
import torch

x = torch.tensor(2.0)                         # input: no gradient needed
w = torch.tensor(-1.0, requires_grad=True)    # leaf parameter
b = torch.tensor(0.5, requires_grad=True)     # leaf parameter

loss = (x * w + b) ** 2                       # forward: graph is recorded
print(loss.grad_fn)                            # <PowBackward...>

loss.backward()                               # backward: fill leaf .grad
print(w.grad, b.grad)                          # tensor(-6.), tensor(-3.)
```

Three object properties tell most of the story:

- `requires_grad`: should operations involving this tensor be recorded?
- `grad_fn`: which recorded operation created this result?
- `.grad`: the accumulated answer for a leaf tensor after `backward()`.

## The lifecycle inside every training loop

```python
optimizer.zero_grad()   # 1. clear answers from the previous batch
loss = loss_fn(model(x), target)  # 2. run forward and record a new graph
loss.backward()         # 3. measure each parameter's effect on loss
optimizer.step()        # 4. use those measurements to update parameters
```

M2 focuses on the first three lines. The next module turns the fourth line into learning.

<Callout type="warn" title="Why clear gradients?">
`backward()` adds into each leaf's `.grad`. That is useful when intentionally combining several mini-batches, but an ordinary training iteration calls `optimizer.zero_grad()` before measuring the next one.
</Callout>
