## What does `torch.compile` add?

TorchDynamo interprets Python bytecode and extracts supported tensor operations into FX graph regions. Python work that cannot be captured remains in rewritten bytecode.

Each cached region has **guards**: assumptions about shapes, dtypes, devices, `requires_grad`, Python values, and other state that must still be true before reuse.

For training, AOTAutograd creates backward graph regions for captured forward regions. Calling `.backward()` still enters the eager autograd engine, which runs compiled backward regions like larger operations.

## What happens at an `if`?

| Condition | Typical behavior |
| --- | --- |
| Python value such as `self.training` | Specialize the graph and guard the value. |
| Tensor metadata such as shape | Specialize it or represent dimensions symbolically. |
| Tensor data such as `x.sum() > 0` | Break capture so Python can obtain a runtime boolean. |
| `torch.cond(pred, true_fn, false_fn, operands)` | Store both restricted branch functions as structured subgraphs. |

A graph break is correctness-preserving. Dynamo compiles the region collected so far, Python executes the unsupported decision, and capture may resume in a continuation.

## Why can another input compile again?

A cached graph is reusable only while its guards pass. A new shape or specialized Python value can fail a guard and produce another compiled entry.

```python
compiled_model = torch.compile(model, dynamic=True)
```

Dynamic shapes can reduce shape-driven recompilation, but operations and shape-dependent branches may still require guards or specialization. Current `torch.compile` documentation describes a default recompilation limit of eight entries before eager fallback for that region.

## When is `torch.cond` appropriate?

Use it when a branch depends on tensor data and both branches satisfy the structured-control-flow contract. Their signatures and output metadata must match, and unsupported mutation or side effects must be removed.

```python
def positive(x):
    return torch.sin(x)

def negative(x):
    return torch.cos(x)

@torch.compile
def forward(x):
    return torch.cond(x.sum() > 0, positive, negative, (x,))
```

`torch.cond` remains a prototype feature, so confirm its restrictions against the PyTorch version you deploy.

## Why can in-place mutation fail backward?

When autograd saves a tensor for backward, it also tracks the tensor's version. An in-place operation increments that version. Backward raises an error if the saved value has changed rather than silently computing the wrong gradient.

```python
x = torch.ones(3, requires_grad=True)
y = x.exp()          # backward needs this output
y.add_(1)            # version changes
y.sum().backward()   # RuntimeError
```

## How do you inspect your program?

```bash
TORCH_LOGS="graph_breaks,recompiles,guards" python train.py
```

Use `torch.compile(fn, fullgraph=True)` when a region should be one graph. It raises at the first break instead of silently continuing with multiple regions.

Then choose deliberately: rewrite the operation, use structured control flow, accept a stable break, or keep that function eager.
